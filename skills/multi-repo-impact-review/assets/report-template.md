# 代码变更影响评审

> **评审结论：通过 / 有条件通过 / 不通过｜风险：高 / 中 / 低｜置信度：高 / 中 / 低**
> 一句话说明影响业务、已证明的问题和合入条件。

## 1. 评审信息

| 项目 | 内容 |
|---|---|
| 项目 / 需求 | 仓库、业务模块、需求或提交 |
| 评审范围 | 每个仓库的基线、目标版本、工作树和变更规模 |
| 影响业务 | 具体业务域和功能 |
| 评审结果 | P0 / P1 / P2 数量及是否允许合入 |
| 核验情况 | CodeGraph 状态、源码核验范围与未执行的运行验证 |

**本次结论**

- **影响什么**：具体业务功能和用户场景。
- **发现什么**：确认的问题；没有问题时明确写“未证明缺陷”。
- **合入条件**：必须修改、确认或验证的事项。

## 2. 业务影响与测试范围

本节只使用业务语言，不出现文件名、函数名、变量名、行号、协议字段或调用链。

| 测试编号 | 业务场景与本次影响 | 测试级别 | 前置条件 | 操作步骤 | 预期结果 | 验证阶段 |
|---|---|---|---|---|---|---|
| T1 | 用户执行的具体业务操作，以及用户或系统行为的变化 | 必测 / 建议回归 / 无需专项回归 | 可复现的账户、数据、配置或环境条件 | 按顺序写清输入与操作 | 可直接观察和判断的结果 | 当前行为核验 / 修复后验收 |

未执行的测试建议不得写成已通过。

**明确不受影响**

- 使用业务语言列出不需要专项回归的页面、接口行为或关联业务。

## 3. 代码审核结果

> **共 N 项：P0 N 项｜P1 N 项｜P2 N 项**
> 给出合入建议。若无问题，明确写“未证明由本次变更引入的缺陷”。

### P1-01｜问题标题

| 开发关注项 | 内容 |
|---|---|
| 代码位置 | 精确仓库、文件、行号和符号 |
| 具体问题 | 错误行为及触发条件 |
| 影响 | 可观察的错误结果 |
| 修改方式 | 开发需要如何修改 |
| 完成标准 | 1–3 个可判断的验收条件 |

仅当文字不足以表达改法时附最小代码示例。
