# 代码变更影响评审

> **评审结论：通过 / 有条件通过 / 不通过｜风险：高 / 中 / 低**  
> 一句话说明影响业务、发现的问题和合入条件。

## 1. 评审信息

| 项目 | 内容 |
|---|---|
| 项目 / 需求 | 仓库、业务模块、需求或提交 |
| 评审范围 | 基线、目标版本、变更规模 |
| 影响业务 | 具体业务域和功能 |
| 评审结果 | 问题数量及是否允许合入 |
| 核验情况 | 已核验范围与未执行的运行验证 |

**本次结论**

- **影响什么**：具体业务功能和用户场景。
- **发现什么**：确认的问题；没有问题时明确写无。
- **合入条件**：必须修改、确认或验证的事项。

## 2. 业务影响与测试范围

本节只给测试人员看。使用业务语言描述操作场景和可观察结果；不得出现文件名、函数名、变量名、行号、协议字段或调用链。

| 业务场景 | 本次影响 | 测试级别 | 预期结果 |
|---|---|---|---|
| 用户执行的具体业务操作 | 用户或系统行为发生了什么变化 | 必测 / 建议回归 / 无需专项回归 | 测试可以直接观察和判断的结果 |

**明确不受影响**

- 使用业务语言列出不需要专项回归的页面流程、接口行为或关联业务。

## 3. 代码审核结果

> **共 N 项：P0 N 项｜P1 N 项｜P2 N 项**  
> 给出合入建议。

### P1-01｜问题标题

| 开发关注项 | 内容 |
|---|---|
| 代码位置 | 精确文件、行号和函数 |
| 具体问题 | 直接指出错误代码行为及触发条件 |
| 影响 | 说明出现的错误结果 |
| 修改方式 | 明确开发需要怎么改；必要的运行时限制放在同一格 |
| 完成标准 | 1–2 个可判断的验收条件 |

仅当文字不足以表达改法时，附一个最小示例：

```diff
- problematic lines
+ corrected lines
```
